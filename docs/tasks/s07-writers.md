## Must have (in this order)

1. **Protection manifest** (ADR 0003, amended by 0007: one per pipeline repo). Done Nov 17 (`tvt report --manifest-dir`). `tvt scan` writes `.tvt/protect.json` per pipeline: every hard keep, keep_high, dormant and record signal it handles with the consumers that protect it (evidence class, rule or dashboard, owner), owner decisions and acknowledged gaps. Deterministic output (sorted, no timestamps beyond `generated_at`) so diffs review cleanly.
2. **Records class.** Done Nov 17 for metrics and streams (schema 23). Spans moved out of S7: protecting them is a property of the pipeline config, so `check` enforces it without reading any span (S8 item 13); an inventory of spans and their cost needs a Tempo reader and is roadmap work. Before S8: confirm the rule in ADR 0011. Audit logs, deploy and change events, Kubernetes audit, and agent tool-call spans (`gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`) are records, detected by name patterns and OTel attributes and declared with `records:` selectors in `tvt.yaml`. `propose` never drops, samples or collapses them. Records protect the span or event, not every byte of it: capping a content attribute (with a truncated marker) and deleting identity attributes are allowed, as long as the outcome fields stay (tool name, success, error, duration, `gen_ai.tool.call.id`). A 40 KB file read stored as a span event is the case this covers.
3. **`tvt propose`** (`pkg/propose`, `pkg/vcs`). Done Nov 17: `--output patch`, every writer below, and `--output pr` (a draft PR per repo from the branch `tvt/propose`; see [docs/propose.md](../propose.md)). Leaving draft waits for S9's approvals. From the JSON report's open recommendations, write the change into each mapped pipeline's repo, one PR per repo, GitHub first (GitLab second, first on the cut list): Prometheus `metric_relabel_configs`, Alloy `prometheus.relabel` and `loki.process`, OTel Collector `filter`/`transform`, Prometheus Operator `ServiceMonitor`/`PodMonitor` `metricRelabelings` (in the monitor, or in the kube-prometheus-stack Helm values that render it; Helm replaces lists, so an overlay first copies the chart's default list for that key from the pinned values), Fluent Bit `grep` Exclude, `modify`/`record_modifier` and `rewrite_tag` (classic `.conf`, YAML, the Helm chart's values and Fluent Operator resources). Each rule carries a comment with the recommendation's claim and monthly saving. Only mapped signals are proposed. `--output patch` writes a patch file with no Git token.
4. **The target build must contain what tvt writes.** Done Nov 17 for the filter processor; `transform`, `logdedup` and `count` follow when tvt writes them. Before writing a `filter`, `transform`, `logdedup` or `count` component, read the Collector distribution (the ocb manifest in the repo, or `components` output); if the component is missing, add it to the manifest in the same PR or report that it can't.
5. **Validate before the PR.** Done Nov 17 (promtool, alloy validate, otelcol-contrib validate, fluent-bit --dry-run, and kubeconform for operator resources). Run the target's own validator on the changed config: `otelcol validate` with the user's distribution, `promtool check config`, `alloy fmt` plus a config load, `fluent-bit --dry-run`. A config that doesn't load never becomes a PR.
6. **Generated OTTL follows safe defaults.** Done Nov 17 for the filter and the delta-counter transform. Stable OTTL v1 syntax and standard functions only (no experimental or lambda functions behind feature gates); `error_mode: ignore`; a `where` clause on every regex statement; explicit casts (`Int`, `String`) where an attribute's type varies between libraries; the narrowest correct context; new processors placed in the enrich, clean, parse, filter, cardinality order. Never write the deprecated `batch` processor: use exporter `sending_queue` batching.
7. **Version-aware templates.** Done Nov 17 (`pipelines[].version`). `tvt.yaml` records each pipeline's Collector version. From v0.164.0 (OTTL v1), templates use stable standard functions only. For an older Collector, use a conservative subset known to behave the same and say in the PR that the target predates OTTL v1. Never use a function promoted after the target's version.
8. **Delta counters and short hashes.** Done Nov 17: label removals (`transform/tvt_aggregate` and `interval/tvt` ahead of `delta_to_cumulative`) and the pseudonymised-ID template (`propose.PseudonymiseStatements`), which no recommendation uses yet. Removing a per-session label (`session.id`, `user.id`) from a delta-temporality metric merges every session into one series, so the generated pipeline deletes the labels, groups, sums per window, then runs `delta_to_cumulative` (which needs points in timestamp order); the summing window must not rely on `batch`, which is removed in v0.177.0. When an ID is pseudonymised instead of deleted, write SHA256 cut to 16 hex characters; a full 64-character hash makes records larger than the UUIDs it replaces.
9. **Match readers on the stored name, through pipeline rewrites.** Done Nov 17: collector filter names, Alloy `prometheus.relabel`, Prometheus `metric_relabel_configs`, OTel `transform` and `metricstransform` metric renames, Alloy `loki.process`, and labels set by pipeline rules (held until tvt places a removal around them). An Alloy or OTel Collector pipeline that renames a metric, label or stream before it's stored (Alloy `prometheus.relabel` and `loki.process`, OTel `transform`, `metricstransform` and `attributes`, Prometheus `metric_relabel_configs` with `replacement`) means readers query a name the source never emits. Read those rewrites from the mapped pipelines, map source names to stored names, and match dashboards, rules and query logs on the stored name; proposals target the point in the pipeline where the name they match exists. A rewrite tvt can't follow (templating, Lua, an OTTL function it doesn't model) is an evidence gap on every signal it could touch, never "no reader". Ground truth: a lab metric renamed in Alloy that only a dashboard reads under its new name stays keep_high. (From the Dash0 maturity-model review: teams compensate for weak source instrumentation with Collector transforms that encode unstated assumptions.)
10. **Generated rules carry their evidence and are regenerated, not hand-edited.** Done Nov 17 for the marked blocks and regeneration; the evidence hash comes from S9 and the hand-edit warning from S8 (`check`). Every rule tvt writes sits inside a marked block (`# tvt:begin <recommendation id>` ... `# tvt:end`) whose comment carries the scan ID, the evidence hash and a one-line reason ("no reader in 30d; 0 rules, 0 panels; $3.10/mo"). The next `propose` rewrites only its own blocks from current evidence, removes blocks whose recommendation was dismissed or whose evidence changed, and leaves everything outside them alone. `check` warns when a block was edited by hand since tvt wrote it.
