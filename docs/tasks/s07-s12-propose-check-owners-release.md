## S7: writers

**Status:** Planned.

**Done when:** `propose` opens a draft PR against the lab pipelines repo for each writer kind.

1. **Protection manifest** (ADR 0003, amended by 0007: one per pipeline repo). Done Nov 17: `tvt report --manifest-dir` (it reads the stored scan; records join in item 2). `tvt scan` writes `.tvt/protect.json` per pipeline: every hard keep, keep_high, dormant and record signal it handles with the consumers that protect it (evidence class, rule or dashboard, owner), owner decisions and acknowledged gaps. Deterministic output (sorted, no timestamps beyond `generated_at`) so diffs review cleanly.
2. **Records class.** Done Nov 17 for metrics and streams (`signals.record`, schema 23; spans wait for a span reader). Audit logs, deploy and change events, Kubernetes audit, and agent tool-call spans (`gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`) are records, detected by name patterns and OTel attributes and declared with `records:` selectors in `tvt.yaml`. `propose` never drops, samples or collapses them. Records protect the span or event, not every byte of it: capping a content attribute (with a truncated marker) and deleting identity attributes are allowed, as long as the outcome fields stay (tool name, success, error, duration, `gen_ai.tool.call.id`). A 40 KB file read stored as a span event is the case this covers. Confirm the rule in ADR 0011 before S8.
3. **`tvt propose`** (`pkg/propose`, `pkg/vcs`). Part 1 done Nov 17: the Prometheus `metric_relabel_configs` and Alloy `prometheus.relabel` drop writers (`propose.Prometheus`, `propose.Alloy`), library only. Part 2 done Nov 17: the `tvt propose` command (`--output patch`, see [docs/propose.md](../propose.md)). Scans store each metric's job values (schema 24); proposable whole-metric drops go into the Prometheus and Alloy pipelines, a block per scrape job (Prometheus) or per pipeline (Alloy), with every other recommendation listed as skipped and why. Part 3 done Nov 17: the OTel Collector writer (`propose.Otelcol`): a `filter/tvt` processor with one exact `metric.name` condition per metric and `error_mode: ignore`, listed first in each metrics pipeline it drops from, checked with `otelcol-contrib validate` 0.165.0. Wired into the command Nov 17 (item 9 part 1): the filter matches every OTel name Prometheus's OTLP translation stores under the recommended name (`propose.OtelConditions`: tokens, unit words, monotonic `total`), checked with `otelcol-contrib validate` and a live 0.165.0 collector that dropped exactly the two matching metrics of four. Part 4 done Nov 17: the Fluent Bit YAML writer (`propose.FluentBitRoutes`): a stream reroute is a `rewrite_tag` to the cold output `pipelines[].cold` names, checked with `fluent-bit --dry-run` 5.2.0 and a live run that moved the debug lines to the cold output. Unread volume streams are signals since Nov 17, so the lab's debug stream reaches it from a scan (and the reconciler's error stream is a confirm question). Still to do: classic `.conf`, Helm and Fluent Operator, ServiceMonitor/Helm writers, and PRs (with S9 approvals). From the JSON report's open recommendations, write the change into each mapped pipeline's repo, one PR per repo, GitHub first (GitLab second, first on the cut list): Prometheus `metric_relabel_configs`, Alloy `prometheus.relabel` and `loki.process`, OTel Collector `filter`/`transform`, Prometheus Operator `ServiceMonitor`/`PodMonitor` `metricRelabelings` (in the monitor, or in the kube-prometheus-stack Helm values that render it; Helm replaces lists, so an overlay first copies the chart's default list for that key from the pinned values), Fluent Bit `grep` Exclude, `modify`/`record_modifier` and `rewrite_tag` (classic `.conf`, YAML, the Helm chart's values and Fluent Operator resources). Each rule carries a comment with the recommendation's claim and monthly saving. Only mapped signals are proposed. `--output patch` writes a patch file with no Git token.
4. **The target build must contain what tvt writes.** Done Nov 17 for the filter processor: `tvt propose` reads the ocb manifest (`pipelines[].build`, or `builder-config.yaml` beside the config) and adds `filterprocessor` at the manifest's contrib version in the same patch; with no manifest it assumes otelcol-contrib and says so. `transform`, `logdedup` and `count` follow when tvt writes them. Before writing a `filter`, `transform`, `logdedup` or `count` component, read the Collector distribution (the ocb manifest in the repo, or `components` output); if the component is missing, add it to the manifest in the same PR or report that it can't.
5. **Validate before the PR.** Done Nov 17 for patches (`pkg/validate`, `tvt propose --validate`): promtool, alloy validate, otelcol-contrib validate and fluent-bit --dry-run, native or in the lab's pinned images; a rejected file stays out of the patch, an unvalidated one is marked. On the writers state all three changed files pass the real validators (`TVT_TEST_VALIDATORS=1`). Run the target's own validator on the changed config: `otelcol validate` with the user's distribution, `promtool check config`, `alloy fmt` plus a config load, `fluent-bit --dry-run`. A config that doesn't load never becomes a PR.
6. **Generated OTTL follows safe defaults.** Done Nov 17 for the filter: `IsMatch` only, `error_mode: ignore`, one path form, linted before writing, never `batch`; the filter goes first (name-only matching, so earliest is cheapest). Stable OTTL v1 syntax and standard functions only (no experimental or lambda functions behind feature gates); `error_mode: ignore`; a `where` clause on every regex statement; explicit casts (`Int`, `String`) where an attribute's type varies between libraries; the narrowest correct context; new processors placed in the enrich, clean, parse, filter, cardinality order. Never write the deprecated `batch` processor: use exporter `sending_queue` batching.
7. **Version-aware templates.** Done Nov 17: `pipelines[].version`; context paths from v0.122.0, bare paths from v0.80.0, refused before; unknown means bare paths and a note. Boundaries checked with `otelcol-contrib validate` on 0.80.0 to 0.165.0 images and live runs on 0.100.0 and 0.165.0. `tvt.yaml` records each pipeline's Collector version. From v0.164.0 (OTTL v1), templates use stable standard functions only. For an older Collector, use a conservative subset known to behave the same and say in the PR that the target predates OTTL v1. Never use a function promoted after the target's version.
8. **Delta counters and short hashes.** Removing a per-session label (`session.id`, `user.id`) from a delta-temporality metric merges every session into one series, so the generated pipeline deletes the labels, groups, sums per window, then runs `delta_to_cumulative` (which needs points in timestamp order). Find a summing window that doesn't rely on the batch processor's timeout before templating it: `batch` is removed in v0.177.0. When an ID is pseudonymised instead of deleted, write SHA256 cut to 16 hex characters; a full 64-character hash makes records larger than the UUIDs it replaces.
9. **Match readers on the stored name, through pipeline rewrites.** Part 1 done Nov 17: backend names to OTel names for the collector filter (see item 3). Part 2 done Nov 17: `tvt scan` reads Alloy `prometheus.relabel` and Prometheus `metric_relabel_configs` rules on `__name__` from a pipeline's `checkout`; renames are followed, and a rule tvt can't follow holds every metric that passes it as unmapped with the reason (writers state: `prometheus.relabel "spans"` holds the 4 span metrics and `target_info`; `shop_search_requests_total` stays keep_high in alloy-apps). Still to do: OTel `transform`/`metricstransform`/`attributes`, Alloy `loki.process`, and label and stream renames. An Alloy or OTel Collector pipeline that renames a metric, label or stream before it's stored (Alloy `prometheus.relabel` and `loki.process`, OTel `transform`, `metricstransform` and `attributes`, Prometheus `metric_relabel_configs` with `replacement`) means readers query a name the source never emits. Read those rewrites from the mapped pipelines, map source names to stored names, and match dashboards, rules and query logs on the stored name; proposals target the point in the pipeline where the name they match exists. A rewrite tvt can't follow (templating, Lua, an OTTL function it doesn't model) is an evidence gap on every signal it could touch, never "no reader". Ground truth: a lab metric renamed in Alloy that only a dashboard reads under its new name stays keep_high. (From the Dash0 maturity-model review: teams compensate for weak source instrumentation with Collector transforms that encode unstated assumptions.)
10. **Generated rules carry their evidence and are regenerated, not hand-edited.** Every rule tvt writes sits inside a marked block (`# tvt:begin <recommendation id>` ... `# tvt:end`) whose comment carries the scan ID, the evidence hash from S9 and a one-line reason ("no reader in 30d; 0 rules, 0 panels; $3.10/mo"). The next `propose` rewrites only its own blocks from current evidence, removes blocks whose recommendation was dismissed or whose evidence changed, and leaves everything outside them alone. `check` warns when a block was edited by hand since tvt wrote it.

## S8: check, the safety gate

**Status:** Planned.

**Done when:** every unsafe case in ground truth is refused, with the reason in the `check` output.

1. **`tvt check`** (`pkg/check`). Evaluates the config in a PR against the manifest, offline, with no credentials: apply Prometheus `metric_relabel_configs` regex semantics (and the same for `ServiceMonitor`/`PodMonitor` `metricRelabelings`), Alloy stages, OTel Collector `filter`/`transform` conditions and Fluent Bit filters to the protected signal set, instead of guessing intent. Fails closed: unknown processors, Lua/WASM and templating it can't render are failures. Fails when the evaluated drop set touches a protected signal or a record, on an unacknowledged evidence gap, on a drop of warn-and-above logs, on a component missing from the target build, on a drop with no recorded owner confirmation, and when the manifest is older than `max_age_days` (default 7). Property tests: random relabel configs; whenever the evaluated drop set overlaps the protected set, `check` must fail. A GitHub Action wraps it.
2. **Error-pattern guard on log rules.** Every generated log drop, sample or collapse rule also keeps lines matching `error|exception|traceback|critical|fatal`, in case a stream's level label is wrong. `check` fails a log rule without the guard.
3. **Least-lossy order enforced.** `check` refuses a drop when a less lossy action from ADR 0010 would keep every reader working.
4. **Replay protected queries before a label removal.** In `propose`, where tvt has backend access: run every protected query that touches the signal twice, as written and with the label removed (`sum without(label)` for counters and histograms; colliding gauges flagged), and compare series counts, label sets, empty results and values beyond a tolerance. The diff goes in the PR body; a query that goes empty or changes its grouping blocks the PR until the owner accepts it.
5. **Lookback and detection limits.** A shorter retention or downsampling tier is refused when any reader (dashboard, rule, agent) has queried further back on that signal. Each alert's worst-case detection delay (scrape interval + range window + rule-group interval + `for` + Alertmanager `group_wait`) is computed and shown in the report; a scrape interval change is refused when any rate or increase window would hold fewer than four samples, when an alert's `for` is shorter than the new interval, or when an alert would pass its severity's detection objective (set in `tvt.yaml`, for example critical 5m).
6. **Collapsed logs keep their counts.** Collapsing repeats changes every `count_over_time`, `rate` or `bytes_over_time` over those lines, so `check` refuses the collapse unless each such query is rewritten to sum the count attribute; `propose` includes the rewrite in the PR.
7. **Attributes must exist where a statement runs.** Refuse a generated filter or transform whose condition reads an attribute no earlier processor or the source provides at that point, and a statement that reads an attribute an earlier statement deleted.
8. **Model existing OTTL instead of failing closed on it** (ADR 0012). Parse the OTTL already in a pipeline so `check` knows what each existing filter drops and each transform deletes, renames or sets. Statements that use lambda or experimental functions, or functions tvt doesn't model, stay fail-closed for the signals they touch.
9. **OTTL conditions in the pipeline are readers.** A routing connector condition, a tail sampling or adaptive tail sampling OTTL policy, a filter condition or a lookup key reads the attributes and streams it names. Each becomes a declared `pipeline_rule` consumer, so dropping or renaming one of those attributes is refused like any hard-keep change.
10. **Connectors chain like recording rules.** The count, sum, signal-to-metrics and spanmetrics connectors turn spans and logs into metrics. A reader of the produced metric also reads the connector's inputs (the stream, and the attributes in its conditions and dimensions), so a log drop that would empty an alerted count metric fails `check`.
11. **Diagnosability after cuts** (should have, optional suite). On a SnowOps Labs cluster (see `lab-backlog.md`), apply the proposed cuts, inject each of its faults, and confirm each is still diagnosable and graded (`labctl incident status`, `labctl scenario verify`). A fault that becomes undiagnosable becomes a ground-truth case in tvt-lab.
12. **Helm overlay safety.** `check` fails a values overlay that loses a drop the chart already had (an overlay list that replaces the chart's default `metricRelabelings` or `cAdvisorMetricRelabelings` without them), and a change to a monitor Prometheus doesn't select.
13. **Records and delta counters.** `check` fails any drop or sample of a record, including a filter on successful tool-call spans, and names the less lossy alternative (cap the content attributes). It allows content caps and identity deletion on records when the outcome fields stay. It refuses a label removal on delta counters when more than one Collector replica receives that data without a load-balancing gateway in front, because only one Collector may see every session.

## S9: owner workflow

**Status:** Planned.

**Done when:** a lab drop goes from draft to ready only after a recorded confirmation, and changing its evidence reopens it.

1. **Owners.** From the ownership map in `tvt.yaml`, CODEOWNERS, `team`/`service` labels and Backstage `catalog-info.yaml` (`spec.owner`, through the component's name or annotations). When none of those name an owner, fall back to OTel resource attributes and Kubernetes metadata: `service.namespace` and `service.name` mapped through `tvt.yaml`, then the workload's `app.kubernetes.io/part-of` and `app.kubernetes.io/name` labels and team labels on its namespace. An owner found this way is marked inferred in the recommendation. A dormant signal with no owner from any source stays report only and is listed as an evidence gap (missing ownership), never routed to a guess.
2. **Draft until confirmed, bound to evidence.** Every drop or label removal opens as a draft PR assigned to its owner. The confirmation, recorded in the protection manifest, includes a hash of the evidence the owner saw (readers, cost, gaps); `check` refuses the merge if the usage graph has changed materially since (a new reader, a gap reopened).
3. **Recommendation status.** Open, confirmed, or dismissed with a reason; a dismissal writes keep plus a review date to the manifest so tvt doesn't ask again. The owner review always asks whether the signal is read only at certain times of year; a yes writes keep plus a review date after the next season.
4. **Decisions expire when their evidence changes.** Each manifest entry (keep, dismissal, confirmation) records the evidence it rested on; when that changes (reader gone, service renamed, owner moved teams), the entry is flagged for re-review instead of persisting or expiring silently. Review dates remain the backstop.
5. **Expected end state.** Each recommendation states what should be true after the merge ("returns no series within an hour of deploy; no rule or panel goes empty; stream bytes fall about 40%"), for the owner to read before merging and for `tvt verify` to check later.
6. **Capped queue and weekly digest** per owner instead of a stream of PRs.

## S10: reduce before drop

**Status:** Planned.

**Done when:** for each lab finding, `propose` picks the least-lossy action that `check` accepts.

1. **Label removal and bucketing.** When a label is always aggregated away, keep the metric and remove the label (vmagent stream aggregation `without:`/`drop_input_labels`, Alloy or Collector equivalents, or a recording rule replacement). When every reader uses only a label's coarse form (`status_code=~"5.."`, a route rather than a raw path), bucket the values in the Collector instead; the replay check confirms readers' results don't change. Stream aggregation also replaces slow recording rules.
2. **Retention and downsampling tiers** for dormant signals before archive and drop: Mimir per-tenant retention, VictoriaMetrics retention filters and downsampling. Respects S8's lookback limit.
3. **Level-based log tiers.** For streams where nothing reads info or debug lines, route levels below warn to the cheapest tier (Loki `retention_stream` or a separate tenant, Fluent Bit `rewrite_tag`, Alloy `loki.process`). A reader of lower-level lines blocks it for that stream.
4. **Collapse with a count, then sample.** The OTel Collector `logdedup` processor collapses identical lines over an interval into one with a count (confirm the count attribute name and settings in the contrib docs first); 1-in-N sampling (Alloy `stage.sampling`, Fluent Bit) comes after it. Each rule carries its saving.
5. **Scrape interval increase.** When every reader of a job's metrics uses a step and range windows well above the scrape interval, raise the job's `scrape_interval` in Prometheus or Alloy instead of dropping anything, within S8's limits.
6. **Staged drops with a revert.** Reroute to the archive first, drop after the quiet period (default 30 days) with no new reader. Every drop PR is generated with its revert PR.
7. **Cap before drop, and keep one copy.** Bytes per attribute key on spans, span events and logs; a large key nothing reads gets a cap (truncate to 512 characters plus a marker attribute), ranked ahead of a drop. One large value carried by two signals in the same trace (a tool's parameters in a log record and a span event, matched by hashes of the values, never the values) gets a proposal to keep one copy.

## S11: savings ledger

**Status:** Planned.

**Done when:** the MVP gate is rehearsed on the lab: merge a tvt PR, and the next scan records measured savings.

1. **Before and after per merged PR:** series or bytes and $/month from the scan before the merge and the first scan after it, stored in the graph and shown in the report.
2. **Savings apart from growth.** What merged PRs saved, separate from what the bill did, with growth attributed to its cause (new metrics, replicas, a release).
3. **Self-hosted results:** GiB freed and how many more days of retention now fit on the same volume (from `retention.size` and the volume size).
4. **Measured from the Collector.** Where a Collector is in the path, read its own exporter telemetry before and after the merge (`otelcol_exporter_sent_log_records_total`, sent spans and metric points, `otelcol_exporter_enqueue_size_bytes`). The bytes metric needs `service.telemetry.metrics.level: detailed` and a `sending_queue`, and it is labelled by exporter, not signal.

## S12: release candidate

**Status:** Planned.

**Done when:** `v0.1.0-rc1` is tagged, and the install guide works on a clean machine.

1. **Supply chain:** reproducible builds verified in CI, cosign-signed releases, govulncheck, gitleaks, Dependabot, and a release checklist in `docs/`.
2. **`SECURITY.md`** (Sprint 2 item 10, if not done) and an install guide checked against a clean install.
3. **Docs for every command.**
4. **The README claim:** "Every signal tvt marks unread had no reader in your evidence window, and every gap is listed. If you find a reader we missed, that's a bug, and the benchmark gets a new case."
5. **Sensitive content note.** In the report, unread attributes whose names mark them as prompts, responses, emails or host paths are flagged beside their saving. tvt reads key names and sizes only, never values.
6. **tvt's own telemetry stays lean.** Signal names and query text stay out of tvt's telemetry by default (the spec's detail level). When opted in, attributes are capped at 512 characters with a truncated marker, and no per-scan or per-signal identifier goes on a metric, so a tvt scan of its own telemetry finds nothing to cut.
