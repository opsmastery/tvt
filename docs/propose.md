# tvt propose

`tvt propose` turns the latest scan's recommendations into config changes for the pipelines in `tvt.yaml` (S7 item 3, ADR 0007). It writes one patch per pipeline repo from local checkouts (`--output patch`, the default, with no Git token), or the patches and then a draft pull request per repo (`--output pr`).

```
tvt propose --db tvt.db --config tvt.yaml \
  --checkout github.com/acme/observability=../observability \
  --dir proposals
git -C ../observability apply ../tvt/proposals/github.com_acme_observability.patch
```

## Flags

| Flag | Meaning |
|---|---|
| `--db` | The scan database (default `tvt.db`). |
| `--config` | `tvt.yaml`, required: its `pipelines:` say where each drop goes. |
| `--checkout repo=path` | A pipeline repo's local checkout, with the repo named as in `tvt.yaml`. Repeat per repo. A pipeline with no checkout is skipped. |
| `--report` | The reviewed report JSON. It must be of the database's latest scan; without it, tvt builds the report from the database (all recommendations, no `--top` cut). |
| `--output` | `patch` (default), or `pr`: the patches, then for each repo a branch `tvt/propose-scan-N` (N: the scan) pushed from its `--checkout` and a draft pull request (see Pull requests below). |
| `--github-api` | The GitHub API root for `--output pr` (default `https://api.github.com`; GitHub Enterprise: `https://HOST/api/v3`). |
| `--dir` | Where patches go (default `proposals`), as `<repo>.patch` with the repo path made filename-safe as in `report.md`'s manifests. |

## Pull requests

With `--output pr`, after writing the patches, tvt does this for each repo that has one:

1. In a temporary worktree of the repo's `--checkout` (the checkout's own working tree is never touched), it fetches the base branch (`pipelines[].branch`, or origin's default branch), applies the patch, commits it as "tvt propose: changes from scan N" with your Git identity, and pushes it to origin as `tvt/propose-scan-N` with your Git credentials. The branch is tvt's: a rerun from the same scan replaces it with one commit, as tvt regenerates its own blocks.
2. Through the GitHub API with `GITHUB_TOKEN` (from the environment, never a flag), it opens a **draft** pull request from `tvt/propose-scan-N` to the base, or updates the title and body of the one already open from that branch. The body lists each recommendation and its claim, the validation results and any Collector build change. Reviewers come from the repo's `pipelines[].reviewers` (`@user`, or `@owner/team` for a team in the repo's organization); a reviewer GitHub refuses is reported, and the PR still opens.

   **Token requirement.** `GITHUB_TOKEN` needs, on the pipeline repos and nothing else: **Contents: write** (to push the branches) and **Pull requests: write** (to open and update tvt's draft PRs, request reviewers, and close or retarget its own earlier PRs, item 3 below). A fine-grained token limited to those repos is the right shape; a classic token needs `repo`. `tvt init` warns when the token reaches more than it needs.
3. Every change comes with its revert (S10 item 6, ADR 0010). Each proposal has its own pair of branches, named by its scan: `tvt/propose-scan-N` carries the change and `tvt/propose-scan-N-revert` one `git revert` commit on top of it, each with a draft PR (the revert PR based on the change's branch, so until the change merges it shows exactly the commit that undoes it). Merging the revert PR puts back what tvt removed and adds nothing, so `tvt check` asks no confirmation for it. A rerun from the same scan updates the same PRs; a later scan's proposal never rewrites an earlier one. Before opening its own, tvt settles its earlier PRs: an open change PR from another scan was never merged and is closed as superseded, with its revert PR; the revert PR of a change that merged is retargeted to the base branch (GitHub does this itself only when the change's branch is deleted); a revert PR whose change closed unmerged is closed. It only touches branches under `tvt/propose`, the old fixed `tvt/propose` and `tvt/propose-revert` included, and leaves every branch in place. If the revert PR can't be opened, the repo is reported as failed even though the change's PR is up.

PRs stay drafts: an owner's confirmation, recorded with the evidence they saw (S9), is what takes one out of draft. Each recommendation's owner is asked for a review too (its `tvt.yaml` `ownership.github` handle, or the owner itself when it's already `@name`), the body lists each row's owner (marked inferred when it is) and evidence hash with the `tvt confirm` steps, and an "After the merge" column with each row's expected end state (`report.md`), and the patch adds `.tvt/proposal.json` (with each row's expected end state for `tvt verify`), which `tvt check` reads to ask for each confirmation (see `check.md`). A repo that fails (no checkout, a patch that doesn't apply on the base, a push or API error) is reported and the other repos still go ahead; the command then exits non-zero, and the patches are in `--dir`. GitHub only; GitLab comes later. The token is only for the API: tvt pushes with the checkout's own Git credentials (an SSH key, say). A fine-grained token needs **Contents: Read-only** (GitHub refuses to open a PR whose refs the token can't read, with a 422 "not all refs are readable") and **Pull requests: Read and write** on the pipeline repos; Metadata: Read comes with them. Make Contents read and write only if the checkout pushes over HTTPS with that same token. Requesting a team as reviewer may also need the organization's **Members: Read**.

**Retention tiers** (S10 item 2): a `retention_tier` row goes into a `prometheus` pipeline's one `remote_write` (`propose.PrometheusTenantTier`): a `write_relabel_configs` drop of the metrics there, and a second `remote_write` named `tvt-dormant` to the same URL with `X-Scope-OrgID: <tiers.dormant_tenant>` that keeps only them. The tenant's retention is Mimir's runtime override, `compactor_blocks_retention_period: <keep_days>d`, which the block's comment asks for; tvt writes only the pipeline. It refuses rather than guess: no `remote_write`, more than one, one with credentials or TLS settings (tvt doesn't copy them), or one that already sends to the tier tenant. Mimir needs `multitenancy_enabled: true` for the header to mean anything. An `alloy` pipeline gets the same in its one `prometheus.remote_write` (`propose.AlloyTenantTier`): a `write_relabel_config` drop in its one `endpoint`, and a second `endpoint` named `tvt-dormant` to the same `url` with `headers = { "X-Scope-OrgID" = <tenant> }` that keeps only them, refusing more than one component or endpoint and any credentials or TLS settings (validated with `alloy validate` 1.10). Other pipeline kinds skip the row with the reason. Checked with `promtool check config`.

**Sampling** (S10 item 4). Rerouting stays the default for an unread stream (Jason's call, Nov 21): it keeps every line, in cheaper storage. Sampling only fills the gap where there's nowhere cheaper to send it. An `alloy` pipeline with no `cold` component and `tiers.sample_one_in: N` in `tvt.yaml` gets the stream's reroute written as a sample: a `tvt_hot` `loki.process` with a `stage.match` on the stream that leaves error-pattern lines outside it (`!~`) and holds `stage.sampling { rate = 1/N }`, forwarding everything to the shipper's original targets. The claimed saving and the expected hot-byte fall scale by 1 - 1/N, and the PR's expectation says the rest are dropped. Without `sample_one_in`, the stream is skipped as before. Other pipeline kinds don't sample yet. Validated with `alloy validate` (1.10).

## What it writes

Only recommendations that are `proposable` (mapped to exactly one pipeline), `drop` actions, and of whole metrics. Each metric's drop goes into the scrape configs of every job it carries: the scan stores the `job` label's values per metric (schema 24). If any of those jobs has no scrape config in the pipeline's `files`, the metric is skipped, because a drop in some jobs would leave the rest of its series and cost in place.

- **Prometheus** (`kind: prometheus`): one `metric_relabel_configs` drop rule per scrape job, naming the metrics that job carries. The block ID is `<pipeline>/<job>`.
- **Alloy** (`kind: alloy`): one `rule` block in each `prometheus.relabel` component the jobs' `prometheus.scrape` components forward to, naming every metric for the pipeline. The block ID is the pipeline's name.

- **OpenTelemetry Collector** (`kind: otelcol`): a `filter/tvt` processor in each file that has a metrics pipeline, listed first in every `metrics` and `metrics/<name>` pipeline, with `error_mode: ignore` (a condition that fails to evaluate keeps the data). The block ID is the pipeline's name. In a flow-style list (`[a, b]`) tvt's entry can't carry marker lines, so a rerun takes `filter/tvt` out of the list before writing again.

  The report has the names Prometheus stores; the collector sees OTel names. Prometheus's OTLP translation splits the OTel name on anything but letters, digits and colons, appends the unit's words (`USD`, `seconds`, `bytes_per_second`, `ratio` for a gauge with unit `1`) and appends `total` to a monotonic counter. So for each stored name the filter matches every OTel name that translates to it: the exact name (a server keeping UTF-8 names), plus `IsMatch` on the tokens with conditions on `metric.unit` and `metric.is_monotonic`. For `coding_agent_cost_usage_USD_total` that matches the monotonic counter `coding_agent.cost.usage` with unit `USD`, and not a gauge or another unit. A name ending `_bucket`, `_sum`, `_count` or `_created` is skipped: it may be one series of an OTel histogram, and the collector can only drop the whole histogram. A case the translation model misses (a unit word already in the OTel name) matches nothing, so its drop is a no-op `tvt check` shows, never a wrong drop.

- **Fluent Bit** (`kind: fluentbit`, YAML config): a stream reroute to cold storage (never a line cut, ADR 0006). For each `reroute` recommendation, tvt finds the Loki output whose static `labels` are exactly the stream's, and adds a `rewrite_tag` filter that retags that output's records (`match: shop.debug`) to `tvt.cold.shop.debug` and keeps no copy. The rule is `$log ^(?!.*(?i:error|exception|traceback|critical|fatal)).*$`: a line naming an error stays hot whatever its tag says (S8 item 2). They leave the Loki output and reach the output `pipelines[].cold` names, by `alias`, which must already exist and whose `match` must take `tvt.cold.*`. tvt doesn't invent a storage destination. It refuses rather than guess: a stream selector with anything but label equalities, a Loki output that matches by wildcard or regex or sets labels from record fields (other streams would move), no cold output, or an input that may not give every record the `log` key `rewrite_tag` tests (tvt takes only `tail` inputs without parsers). A file ending `.conf` is read and written in the classic format: the same checks, and a `[FILTER]` section (`Name rewrite_tag`, `Match`, `Rule`, `Emitter_Name`) before the first `[OUTPUT]`; `@INCLUDE` is refused (list the included files instead). Checked with `fluent-bit --dry-run` and a live 5.2.0 run (Nov 18, with the guard) that moved the ordinary tailed lines to the cold output and kept the `ERROR`, `Traceback` and `Fatal` lines on the hot one. With `helm_values` (the fluent/fluent-bit chart), tvt checks each route against the overlay's `config.inputs`, `config.filters` and `config.outputs` joined as the chart joins them (the chart's defaults for any the overlay doesn't set), and writes the `[FILTER]` into `config.filters`. Helm replaces the string, so when the overlay doesn't set `config.filters`, tvt creates it starting with the chart's default filters from `helm_values.defaults` (`helm show values fluent/fluent-bit`), or the chart's `kubernetes` filter would go. Checked by rendering chart 0.58.3 with `helm template` and dry-running the rendered `fluent-bit.conf` in Fluent Bit 5.2.0. The values file itself is marked NOT VALIDATED, since only the chart renders it. In most Kubernetes deployments the chart's `tail` input uses `multiline.parser` and Loki labels come from record fields, which tvt refuses to reroute by tag; the writer fits static inputs and outputs. A file holding Fluent Operator resources (`fluentbit.fluent.io/v1alpha2`) gets a `ClusterFilter` named `tvt-cold-<tag>` with a `rewriteTag` filter, appended after a `---` in a marked block and carrying the labels of an existing `ClusterFilter` (so the `FluentBitConfig` selector picks it up). The same checks run on the resources: the Loki `ClusterOutput` with exactly the stream's static labels and an exact `match`, a cold `ClusterOutput` named by `pipelines[].cold` whose `match` takes `tvt.cold.*`, and a `tail` `ClusterInput` with that tag and no parser. The operator builds the Fluent Bit config, so tvt checks the resources with kubeconform against the Fluent Operator schemas instead of a dry run; the writer isn't yet checked against a running operator. Reroutes come from the scan: an unread stream from the volume API is a stream signal of its own (see `report.md`).

- **Alloy stream reroutes** (`kind: alloy`): Alloy has no per-stream route inside `loki.process`, so tvt splits the stream off where the one `loki.process` that forwards to a `loki.write` sends it. That component's `forward_to` points at two components tvt adds: `loki.process "tvt_hot"` drops the stream's lines with a `stage.match` (a selector on its exact label values plus a line filter `!~ "(?i)error|exception|traceback|critical|fatal"`, so error lines stay hot whatever their level label says, S8 item 2) and forwards everything else to the original targets, and `loki.relabel "tvt_cold"` keeps only the stream and forwards it to the component `pipelines[].cold` names (such as `loki.write.cold`), which must exist in the file. The original `forward_to` line is kept in the block as a `tvt:original` comment, and removing the block puts it back. A rule on label values also matches a stream that carries those values plus other labels, so check `tvt why` for streams with extra labels. tvt refuses rather than guesses when more than one `loki.process` ships to Loki or `forward_to` spans lines. Checked with `alloy validate` and a live Alloy 1.10.0 (Nov 18, with the guard): the stream's ordinary lines reached only the cold `loki.echo`, and its `ERROR`, `Traceback` and `Fatal` lines stayed hot (the cold side keeps a copy of them too).

- **Prometheus Operator** (`kind: prometheus-operator`, `files` of ServiceMonitor and PodMonitor manifests): a `metricRelabelings` drop rule on every endpoint of each monitor whose targets carry the metric's jobs, appended to an existing list or added as the key. tvt works out each monitor's `job` from the manifests: a PodMonitor's is `<namespace>/<name>`; a ServiceMonitor's is, for each Service it selects in the files, the Service's label named by `spec.jobLabel`, or else the Service's name. A monitor whose job it can't tell (its Service isn't in the files, as with the apiserver's `default/kubernetes`; a selector with expressions; a PodMonitor `jobLabel`; an endpoint relabeling that sets `job`) maps to nothing until `pipelines[].monitor_jobs` names it (`apiserver: ServiceMonitor/monitoring/kps-kube-prometheus-stack-apiserver`), and a metric with such a job is skipped. The changed manifests are checked with kubeconform against the monitor schemas (see Validation); other kinds in the file are counted as not checked. With `helm_values` (`file`: your kube-prometheus-stack overlay, `path`: the chart's key in an umbrella chart's values or empty, `defaults`: the chart's own `values.yaml` at the deployed version, from `helm show values`), the drops go into the overlay instead, and `files` lists the chart's rendered output (`helm template`), read only to resolve jobs to monitors. Each monitor's rule goes into the values keys that render its endpoints' `metricRelabelings` (the kubelet's three: `metricRelabelings`, `cAdvisorMetricRelabelings`, `probesMetricRelabelings`), checked at chart 93.3.0 by rendering with a sentinel rule in every key. Helm replaces a list rather than merging it, so a key your overlay doesn't set yet is created with the chart's default rules first (the apiserver's bucket drops, the kubelet's cAdvisor drops); a key it sets gets tvt's rule appended. Without `defaults`, the pipeline is skipped. `TestHelmValuesRender` (`TVT_TEST_HELM=1`) renders the chart with an edited overlay and checks each monitor's rules, defaults included.

- **Label removals in Prometheus and Alloy**: a `label_removal` whose series stay unique without the label (`removal: labeldrop`) becomes a relabel rule that empties the label on that metric only (`source_labels: [__name__]`, `regex: <metric>`, `target_label: <label>`, `replacement: ""`, `action: replace`), in the same block as the job's drops, so the job's other metrics keep the label. Checked with Prometheus's own relabel engine: the label goes from the named metric and stays on others. A removal that merges series (`removal: aggregate`) is skipped: a relabel rule can't sum the merged series, so it needs a recording rule or a collector's ordered pipeline (see below). `job`, `instance` and `__` labels are never removed.

Each rule sits in a marked block (S7 item 10):

```
# tvt:begin prometheus-scrape/node scan=12 evidence=3f9c0a1b2d4e
# 3 unread metrics, see tvt why; saves 41.20 USD/month
- source_labels: [__name__]
  regex: "node_a|node_b|node_c"
  action: drop
# tvt:end
```

`evidence` is a short hash of the scan and the recommendations' evidence; S9 binds approvals to it. Every existing tvt block in a file is removed before the new ones go in, so a rerun replaces the last proposal instead of stacking on it, and every other byte of the file is kept. The patch starts with the recommendations it carries and their claims; `git apply` skips that text.

## Replaying protected queries before a label removal

With `--replay-prom URL` (S8 item 4), before writing a label removal tvt runs every protected query that reads the metric twice against that Prometheus: as written, and with the label removed (the query rewritten to wrap the metric in `sum without(label)`). It compares series counts, label sets, empty results and values. A query that goes empty or changes its grouping keeps the removal out of the patch, and the diff goes in the PR body as "<repo> replay: …". A removal on a gauge is flagged (summing gauges that collide changes their meaning). Without the flag, the PR says the replay wasn't run.

Replays mark themselves twice so the next scan doesn't count them as usage: a leading PromQL comment `# tvt-replay` (kept verbatim in Prometheus' query log) and the `X-Query-Tags: Source=tvt-replay` header. The Prometheus and Mimir query-log readers drop both.

A pipeline the scan records as more than one Collector replica with no load-balancing gateway in front (`pipelines[].replicas`, `load_balanced: false`) gets no label removals: each replica would sum a different share of the sessions (S8 item 12).

## Label removals on delta counters

A `label_removal` recommendation on an OTel Collector pipeline (S7 item 8) is written as an ordered pipeline, never a plain label drop. Removing a per-session label (`session.id`, `user.email`) from a delta counter merges every session into one series. After `delta_to_cumulative` that breaks the counter; before it, the merged deltas must be summed over a window, because sessions export separately and `delta_to_cumulative` keeps one point per stream and interval. So tvt adds, just ahead of `delta_to_cumulative` in each metrics pipeline:

1. `transform/tvt_aggregate`: `delete_matching_keys(datapoint.attributes, "^session[^A-Za-z0-9:]+id$") where <the metric's conditions>`, one statement per label, matching the OTel attribute names that translate to the Prometheus label.
2. `interval/tvt` with `interval: 60s` (the OTel SDKs' default export interval), which sums each merged stream's deltas over the window.

Checked on a live otelcol-contrib 0.165.0 with two sessions sending 5 and 3 tokens a round for three rounds. With the window, the cumulative series read 8, 16, 24 whether the sessions exported together or apart. Without it, apart, it read 5, 10, 15: one session lost each round. A pipeline with no `delta_to_cumulative` is refused (no delta counter to protect), and so is a Collector before v0.122.0 (the oldest the ordered pipeline was validated on). A custom build gets `transformprocessor` and `intervalprocessor` added to its manifest. Pseudonymising an ID (SHA256 cut to 16 hex characters) instead of deleting it waits for a recommendation that asks for it.

A `bucket` recommendation (S10 item 1: every reader uses the label only by class, such as `status_code=~"5.."`) goes into the same ordered pipeline. Bucketing merges series just as a removal does (every 5xx code becomes one series), so it needs the same window. `transform/tvt_aggregate` gets, ahead of any deletes, `replace_pattern(datapoint.attributes["<label>"], "^([0-9])[0-9][0-9]$", "$${1}00") where <the metric's conditions>` for every OTel spelling of the label: `replace_pattern` takes one exact key, and each underscore in the stored name may have been an underscore or a dot (`http_response_status_code` comes from `http.response.status_code`), so a label with three underscores gets eight statements. A label with more than four is refused. Each spelling first gets `set(<attr>, String(<attr>)) where IsInt(<attr>) and (<conditions>)`: semantic conventions make status codes ints, and `replace_pattern` leaves an int alone. Checked live on otelcol-contrib 0.165.0 with two delta rounds of an int `503` (5), a string `502` (3) and an int `200` (7) through the ordered pipeline: without the cast the Prometheus exporter showed `500` 6 and `503` 10; with it, `500` 16 and `200` 14 (the cast changes no label, since Prometheus renders an int and its string the same). Only three-digit values change; `500` stays `500`, so a rerun changes nothing, and a reader's `5..` matcher still matches. The `$$` is the Collector's escape for a literal `$` in its config. `job`, `instance`, `__` labels and histogram series are refused. On any other pipeline kind the row is skipped with the reason: a relabel rule can rewrite the value but can't sum the merged series (stream aggregation comes later). `TestProposeBucket` writes it on the lab's Collector and, with `TVT_TEST_VALIDATORS=1`, runs `otelcol-contrib validate` on the result; `TestCheckBucket` checks that `tvt check` accepts it.

Pseudonymised IDs (S7 item 8) are a template with no recommendation that asks for them yet: `propose.PseudonymiseStatements` writes, for each key in a context (`span`, `spanevent`, `log`, `datapoint`, `resource`), `set(<ctx>.attributes["k"], Substring(SHA256(String(<ctx>.attributes["k"])), 0, 16))`, only where the value is set and isn't already 16 lowercase hex characters (so an agent and a gateway don't hash twice). Sixteen hex characters, not the full 64: a full hash makes records larger than the UUIDs it replaces. The value is cast with `String`, since an ID's type varies between libraries. The statements need Collector v0.122.0 or later and pass `otelcol-contrib validate` on v0.122.0 and v0.165.0 (`TestPseudonymiseValidate`); an unknown or older version is refused.

## Scrape intervals

The report's `intervals` rows with a proposal (S10 item 5) are written into the scrape config of the pipeline that carries the job (the pipeline targets of its metrics; a job spread over several pipelines, or a job with no scrape config in the pipeline's files, is skipped with the reason). `PrometheusIntervals` sets `scrape_interval` on the scrape config; `AlloyIntervals` on the job's `prometheus.scrape` component (job from `job_name`, else `prometheus.scrape.<label>`, Alloy's default). A job's own `scrape_interval` line moves into the block as a `tvt:original` comment, so stripping the block restores the file byte for byte; a job without one gets the key at its end, outside any drop block. Interval blocks are IDed `interval:<job>`, and their writers strip only their own blocks (`stripBlocksIf`), so propose writes the drops first (which strip every block) and the intervals after them, in the same file pass; a file with only intervals still gets the Alloy reroutes. Other pipeline kinds skip them. The output and the PR body list each one as `interval:<job>` with why tvt stopped there; `.tvt/proposal.json` leaves them out, since nothing is dropped and no owner confirmation is needed. The manifest's `scrape_limits` let `check` refuse an increase past what the readers allow. `TestIntervalsValidate` (`TVT_TEST_VALIDATORS=1`) runs promtool and alloy on the writers' output; `TestProposeIntervals` covers the propose path and the manifest limits.

## Collapsing repeated lines (library only)

`propose.OtelcolDedup(src, logsPipelines, d)` (S10 item 4) adds `log_dedup/tvt`, first in each named logs pipeline: `interval` 1m (the processor's default is 10s), `log_count_attribute: log_count`, and one condition per service, `resource.attributes["service.name"] == "<service>" and not (<record match>)` for each record log-event match (bare `attributes`, `body` and severity paths qualified with `log.`). An unscoped dedup is refused, and so is a Collector before v0.122.0 or with no `pipelines[].version`. Its blocks are IDed `dedup:<name>` and it strips only its own (run it after `OtelcolChanges`). Checked live on otelcol-contrib 0.165.0: five identical reconciler lines became one record with `log_count` 5, while three identical `tool_result` record events from the same service and another service's lines passed through untouched. `TestOtelcolDedupValidate` runs `otelcol-contrib validate`; `TestCheckDedup` shows check accepting it on the lab's Collector with records excluded and refusing it without. `tvt propose` writes the report's `collapse` rows with it (Nov 21): in an `otelcol` pipeline (v0.122.0 or later), for a stream whose one label is `service_name`, into the one logs pipeline that ships to an exporter, with the record matches excluded; the builder manifest gets `logdedupprocessor`. Other pipeline kinds skip the row with the reason. 1-in-N sampling comes next.

`propose.OtelcolTier(src, logsPipeline, t)` (S10 item 3) sends a stream's lines below warn to the cold tier and keeps the rest hot. It adds `filter/tvt-tier-hot` first in the named logs pipeline, dropping the tier's lines there, and a pipeline `logs/tvt-tier` with the same receivers and processors behind `filter/tvt-tier-cold`, which keeps only the tier's lines, exporting to the exporter `pipelines[].cold` names (it must exist in the file, and the hot pipeline mustn't already export to it). A line is in the tier when its service is one of the tier's, its `severity_number` is set and below 13 (warn), its body is a string that doesn't match `(?i)error|exception|traceback|critical|fatal`, and it matches no record log-event condition. Anything else stays hot: a line with no severity number, a structured body, an error line at debug, a record, another service's line, and a line whose condition fails to evaluate (`error_mode: ignore`). Collectors before v0.122.0 get bare paths. Its blocks are IDed `tier:<name>` and it strips only its own (run it after `OtelcolChanges`). Checked live on otelcol-contrib 0.165.0 (Nov 21): of the coding agent's lines, the plain debug and info lines reached only the cold exporter; its warn line, a debug line naming an exception, a `tool_result` record at info, a line with no level, one with a map body and another service's debug line stayed hot. `TestOtelcolTierValidate` runs `otelcol-contrib validate`. `tvt propose` writes the report's `level_tier` recommendations with it (Nov 21): in an `otelcol` pipeline with `cold` set, for a stream whose one label is `service_name`, into the one logs pipeline that ships to an exporter (`propose.OtelcolLogsShipper`; several are refused), with the built-in and `records.log_events` record matches kept hot. A pipeline of another kind, or with no `cold`, skips the row with the reason. The proposal file carries the row, so check asks for the owner's confirmation. In Fluent Bit and Alloy pipelines a `level_tier` row is the stream's reroute with a level filter (Nov 21): only lines that name a level below warn as a key move, by `propose.LevelLinePattern` (logfmt `level=debug`, JSON `"level":"info"`, `lvl` or `severity` too, any case; it doesn't parse quotes, so a level key inside a quoted message counts). A line that names no level that way stays hot, so these writers move no more than the line says; Loki's `detected_level` also guesses from bare words, so the report may count more than moves. Fluent Bit's `rewrite_tag` rule adds a lookahead, `^(?!.*(?i:error|...))(?=.*(?i:<level pattern>)).*$`; Alloy's `tvt_hot` stage adds `|~ "<level pattern>"` after the guard. The Alloy cold side still keeps the whole stream, so warn-and-above lines are copied there too. Checked live on Fluent Bit 5.2.0 (Nov 21): `level=debug`, JSON `"level":"info"` and `level=INFO` lines went to the cold output; a warn line, a debug line naming an exception, a bare `DEBUG` word, a JSON error line and `level=debugging` stayed hot. `alloy validate` and `fluent-bit --dry-run` pass in the tests.

## OTTL by Collector version

`pipelines[].version` in `tvt.yaml` records the Collector version (S7 item 7), and picks how the filter's conditions are written. Each boundary was checked with `otelcol-contrib validate` on the real image, and both forms were run on live Collectors, which dropped exactly the matching metric:

| Version | Conditions |
|---|---|
| v0.122.0 and later | context-qualified paths: `metric.name`, `metric.unit`, `metric.is_monotonic` (v0.121.0 and v0.120.0 reject them) |
| v0.80.0 to v0.121.x | bare paths: `name`, `unit`, `is_monotonic` |
| before v0.80.0 | refused: older images have no `validate` command, so tvt has no template it has checked for them |
| not set | bare paths, which every checked version accepts (v0.80.0 through v0.165.0), and the patch says to set the version |

Every condition follows S7 item 6: stable standard functions only (`IsMatch`), no experimental or lambda functions, `error_mode: ignore`, and one path form per filter; tvt checks this before writing. tvt never writes a `batch` processor. The filter goes first in each pipeline rather than after enrich and clean processors: it matches only names as receivers emit them, so dropping before any other processor spends work on the data is both safe and cheapest. A pipeline that renames metrics in a `transform` before they're stored is a rewrite (S7 item 9), which tvt doesn't read for collectors yet.

## Custom Collector builds

A Collector built with ocb has only the components its builder manifest lists, and a config naming any other doesn't load (S7 item 4). Before tvt writes `filter/tvt`, it reads the pipeline's manifest: `pipelines[].build` in `tvt.yaml` (a path in the repo), or a `builder-config.yaml` next to one of the pipeline's files. If the manifest doesn't list `github.com/open-telemetry/opentelemetry-collector-contrib/processor/filterprocessor`, the same patch adds it, in a marked block, at the version the manifest's other contrib components use (or its core `v0` components', or `dist.otelcol_version`). Rebuild the Collector before deploying the config. A manifest with no version to match skips the pipeline: tvt doesn't guess a module version. With no manifest, tvt assumes `otelcol-contrib`, which includes the filter processor, and the patch header says so.

## A capped queue per owner

With `tvt.yaml` `queue.per_owner: N` (S9 item 6), propose writes at most N open recommendations per owner per run, each owner's highest savings per minute of checking first; the rest are skipped as `queued` and come up once those are decided (confirmed or dismissed rows stop counting). Unowned rows share one queue. Without it, propose writes every proposable row.

## What it skips, and says so

Every other recommendation is printed as skipped with the reason: unmapped or claimed by several pipelines, a recording rule's output, an action or signal kind with no writer yet (label removals, stream reroutes), a pipeline kind with no writer yet (OTel Collector, Fluent Bit, exporters), Helm-rendered pipelines, a missing checkout, or a scan that didn't read the job label.

## Validation

A config that doesn't load never goes into a patch (S7 item 5). For each changed file, tvt copies the pipeline's checkout (without `.git`) to a scratch directory under your cache directory, writes its changes in, and runs the pipeline's own validator there, so references to other files resolve:

A Collector started with `--feature-gates` (for an experimental OTTL function such as `ToValidUTF8`) needs the same gates in `pipelines[].feature_gates`: tvt passes them to `otelcol-contrib validate`, or every changed config fails to load. Found on the lab, whose Collector needs `pkg.ottl.functions.enableExperimental` since tvt-lab #40.

| Kind | Validator | Image when it isn't on PATH |
|---|---|---|
| `prometheus` | `promtool check config <file>` | `prom/prometheus:v3.5.0` |
| `alloy` | `alloy validate <file>` | `grafana/alloy:v1.10.0` |
| `otelcol` | `otelcol-contrib validate --config=<file>` | `otel/opentelemetry-collector-contrib:0.165.0` |
| `fluentbit` | `fluent-bit --dry-run -c <file>` | `fluent/fluent-bit:5.2.0` |
| `prometheus-operator`, and `fluentbit` files of Fluent Operator resources | `kubeconform -strict` against the custom resource schemas tvt ships | `ghcr.io/yannh/kubeconform:v0.8.0` |

The binary on PATH wins; otherwise the image runs through podman or docker (`--container-runtime`), with no network and the copy mounted read-only. Validate with your own distribution and version with `--validator-image otelcol=ghcr.io/acme/otelcol:1.2.3`. The images are the versions the tvt lab runs. The kubeconform schemas (Prometheus Operator `ServiceMonitor`, `PodMonitor` and `Probe`, and the Fluent Operator resources) are embedded in tvt from datreeio/CRDs-catalog at a pinned commit and work offline; resources of any other kind in the file are skipped and the summary says how many (override the image with `--validator-image kubernetes=...`).

- A file the validator rejects is left out of the patch, and its recommendations are listed as skipped with the validator's first lines.
- With `--validate auto` (the default), a file no validator could check is still written, and the patch header and the summary mark it `NOT VALIDATED` with the reason. `--validate require` skips it instead; `--validate off` skips validation.

The writers also check their own output first: the Prometheus writer re-reads it, the Alloy writer re-parses it, and the collector writer confirms the filter is first in each pipeline.
